# AGENTS.md — SkillTracer

> Agent-facing guide for the SkillTracer repository. This file describes the project as it is today, not as it is planned to become. Read this before making code changes.

---

## 1. Project overview

**SkillTracer** is a life-tracking platform. The goal is to let users track habits, tasks, expenses, time, and skills through a Telegram bot and a web dashboard.

The repository is a multi-service Docker application:

| Service | Path | Technology | State |
|---|---|---|---|
| Backend API | `backend/` | FastAPI + SQLAlchemy 2.0 (async) + PostgreSQL 16 | Auth (Telegram OAuth + JWT), User model, Alembic migrations, tests |
| Telegram Bot | `bot/` | aiogram v3 + httpx | Active — FSM implemented (entry flow: rating → comment → photo → confirm) |
| Web Dashboard | `frontend/` | React 18 + TypeScript + Vite + Tailwind CSS | Skeleton — only `App.tsx`, `main.tsx`, and `index.css` have code |
| Reverse Proxy | `nginx/` | Nginx | Configured for `skilltracer.art-artel.su` |
| Infrastructure | `docker-compose*.yml`, `scripts/` | Docker + Docker Compose + Certbot | Dev/prod compose files + Ubuntu setup scripts |

All user-facing documentation and comments in the repository are written in **English**. Task metadata (`TASK.md`, `CONTEXT.json`) contains Russian instructions generated by the Voyage AI Framework, but those are project-management artifacts, not code conventions.

## 4. Code organization

### 4.1 Backend (`backend/app/`)

- **Entry point:** `app.main:app`.
- `app/main.py` creates a `FastAPI` instance, enables open CORS, exposes `GET /` and `GET /health`, and mounts `/api/v1/auth`.
- **Implemented:** `models/user.py`, `models/schemas.py`, `routers/auth.py`, `services/auth.py`, `deps.py`, `config.py`, `database.py`, and Alembic migrations under `alembic/versions/`.
- **Authentication:** Telegram Login Widget hash verification, JWT access tokens (`python-jose`), and a `GET /api/v1/auth/me` protected route.
- **Explicit `__init__.py` files** exist under `backend/app/` and its subdirectories to keep `mypy` happy.

### 4.2 Bot (`bot/app/`)

**Status:** Active — FSM implemented

- **Entry point:** `python -m app.main`.
- `app/main.py` — Dispatcher, entry router connected via `dp.include_router(entry.router)`.
- `app/config.py` — Settings: `TELEGRAM_BOT_TOKEN`, `BACKEND_URL`, `BOT_API_TOKEN`.
- `app/handlers/entry.py` — FSM: `EntryStates` (rating → comment → photo → confirm), `/entry` and `/cancel` commands.
- `app/services/backend.py` — `BackendClient` (httpx): `authenticate`, `get_categories`, `create_entry`, `upload_media`.

**Commands:** `/start`, `/entry`, `/cancel`

**Inline buttons:** 🔴1 🟠2 🟡3 🟢4 🟢5 (rating selection)

**Commits:** f7873f5 (FSM + BackendClient), acf0319 (__init__.py packages)

### 4.3 Frontend (`frontend/src/`)

- **Entry point:** `src/main.tsx` renders `<App />` inside `React.StrictMode`.
- `src/App.tsx` is a placeholder landing page with a counter button.
- `src/index.css` contains only Tailwind directives.
- **Planned but empty:** `api/`, `components/`, `hooks/`, `pages/`, `store/`.
- `App.tsx` imports `./App.css`, but that file does not exist. This will break `npm run build` until the import is removed or the file is created.

## 5. Build and run commands

### 5.1 Full stack (Docker)

```bash
# Local development
cp .env.example .env
# Edit .env, then:
docker compose up -d

# Production-like
docker compose -f docker-compose.prod.yml up -d
```

After `docker compose up -d`:

- Backend Swagger UI: http://localhost:8000/docs
- Frontend dev server: http://localhost:3000
- Nginx (HTTP): http://localhost

### 5.2 Backend (local)

The project provides both Poetry (`pyproject.toml`) and pip (`requirements.txt`) metadata. The CI and Dockerfiles use **pip + requirements.txt**.

```bash
cd backend

# Install
pip install -r requirements.txt

# Run (matches Docker CMD)
uvicorn app.main:app --host 0.0.0.0 --port 8000 --reload

# If using Poetry
poetry install
poetry run uvicorn app.main:app --host 0.0.0.0 --port 8000 --reload
```

### 5.3 Bot (local)

```bash
cd bot
pip install -r requirements.txt
python -m app.main
```

Requires `TELEGRAM_BOT_TOKEN` in the environment or `.env`.

### 5.4 Frontend (local)

```bash
cd frontend
npm install
npm run dev          # Vite dev server on 0.0.0.0:3000
npm run build        # Type-check + bundle to frontend/dist/
npm run preview      # Preview the production build
npm run lint         # ESLint with zero warnings allowed
```

## 7. Code style guidelines

The repository relies on the following tools. `mypy` is configured in `backend/pyproject.toml`; `ruff` and `eslint` use their default/flat configs:

- **Python linting/formatting:** `ruff`
- **Python type checking:** `mypy`

### 7.1 Style commands

```bash

# Frontend

```

### 7.2 Project-specific rules (from `TASK.md` / `CONTEXT.json`)

When writing new code, follow these rules. They are enforced by project conventions:

1. **All async functions must have type hints.**
2. **Use `async_sessionmaker` + `AsyncSession`** for async SQLAlchemy database access.
3. **Never use `eval()`, `exec()`, or `compile()` with user input.**
4. **All secrets must be loaded through pydantic-settings + `.env`.**
5. **Every new function longer than 10 lines must have at least one test.**

### 7.3 General conventions

- Use English for code comments, docstrings, commit messages, and user-facing docs.
- Keep modules small and domain-focused. The empty `models/`, `routers/`, `services/`, `handlers/`, `components/`, etc. directories indicate the intended modular structure.
- Prefer explicit `__init__.py` files in new Python packages.
- Do not change files outside the task-relevant set unless explicitly required.

## 8. Security considerations

- **CORS is currently open:** `backend/app/main.py` sets `allow_origins=["*"]`. Restrict this before any real deployment.
- **Default secrets:** `.env.example` and `docker-compose.yml` contain placeholder secrets (`changeme`, `your-super-secret-key-here-min-32-chars`). Replace them in production via `.env`.
- **Authentication is implemented** via Telegram OAuth hash verification and JWT access tokens. `passlib` is still unused (reserved for future password-based flows).
- **Secrets handling:** load all secrets through pydantic-settings from `.env`. Do not hard-code credentials.
- **Input safety:** never pass user input to `eval()`, `exec()`, or `compile()`.
- **Nginx:** `nginx/default.conf` currently listens only on HTTP (port 80). HTTPS is intended to be added via Certbot after the initial server setup.

## 9. Deployment

### 9.1 Development

Use `docker compose up -d`. Volumes mount source code for live reload:

- `backend/` → `/app`
- `bot/` → `/app`
- `frontend/` → `/app` (with `node_modules` preserved in a Docker volume)

### 9.2 Production

Use `docker-compose.prod.yml`:

- Backend runs under Gunicorn with Uvicorn workers:
  ```
  gunicorn app.main:app -w 4 -k uvicorn.workers.UvicornWorker -b 0.0.0.0:8000
  ```
- No source-code volumes are mounted (immutable containers).
- Frontend is built inside its Dockerfile; Nginx serves `frontend/dist/`.
- PostgreSQL and Certbot data are persisted with named volumes.

### 9.3 Server bootstrap

Two helper scripts target an Ubuntu 24.04 server:

- `scripts/setup_server.sh` — full bootstrap (system update, Docker, Compose, Nginx, Certbot, UFW, user creation, repo clone to `/opt/skilltracer`).
- `scripts/setup_server_quick.sh` — shorter version.

After running either script, copy `.env.example` to `.env`, fill in real values, start the stack, and run Certbot for HTTPS.

- `frontend/src/App.tsx` imports `./App.css`, but the file does not exist. Fix this before the first production build.
- `docs/` is empty and `docs/architecture.md` is referenced by `README.md` but does not exist.

- Backend has a working database connection, `User` model, Alembic migration, and Telegram OAuth/JWT authentication.
- Bot FSM is implemented but not yet tested in a real Telegram environment (Docker volume mount only).
- Frontend has no routing, state management, API client, or tests despite the corresponding libraries being installed.

When adding features, keep changes minimal, follow the project-specific rules in section 7.2, and update this file if you introduce new conventions, commands, or architecture decisions.
